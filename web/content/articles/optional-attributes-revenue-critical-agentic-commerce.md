In agentic commerce, **optional often means “conditionally mandatory”**: agents use sparse attributes as hard filters. Paladio treats optional attribute gaps as **readiness defects** surfaced by the Attribute Agent and readiness scoring—not as nice-to-have enrichment backlog.

PIM admin toggles “optional” while **Voomi**-scale matching treats electrical/pack fields as hard gates on **1M+ SKUs → 200M+ ASINs**; **Profitero** pipelines treat sparse vendor columns as model inputs required for **>95% P/R** across **80+ languages**; **JCPenney** Mirakl facets treat “optional” supplier fields as mandatory browse keys. Revenue teams never see the exclusion because analytics tools do not join **facet/filter logs** to **attribute coverage**.

## Proof Points

- **Profitero:** “optional” vendor fields became ranking/filter signals across **80+ languages**—**>95% precision/recall** required treating sparse fields as model inputs, not footnotes.
- **Voomi Supply:** **1M+ SKUs**; a “minor” HVAC attribute (e.g., electrical) is often a **hard filter** in matching **200M+ ASINs**—absence = exclusion from publish batch.
- **JCPenney:** multi-brand onboarding—**taxonomy alignment** exposes “optional” attributes that are mandatory for Mirakl browse paths.
- **Failure scenario:** **Missing BTU range** on two visually similar HVAC SKUs → the agent (or marketplace filter) keeps only the fully-specified SKU in the consideration set—same pattern as **Voomi**-scale publish batches where incomplete electrical attributes stall **200M+ ASIN** matching, and as **Profitero** pipelines where sparse fields break **>95% P/R** unless modeled as first-class inputs.
